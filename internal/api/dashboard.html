DepScan
How it works
Scans folders inside

Which dependencies would block this build?

Paste the folder of a Go or npm project. DepScan reads go.mod and package-lock.json, checks every package against OSV.dev, and applies your policy.yaml.

You get one row per package with the version to upgrade to. New here? The walkthrough below shows each step.

Scanning

Large repositories can take a minute: every advisory is fetched from OSV.dev.

How a scan works

From a folder path to a pull request check, in nine steps. Use the arrows, swipe, or let it play.

Step 1 of 9

Paste a project folder

Point DepScan at any folder inside your scan root and press Scan. Nothing is uploaded: the server reads the files where they are.

Step 4 of 9

Advisories come from OSV.dev

Every package version is checked against OSV. When two databases describe the same bug, the copies are merged into one finding, so counts stay honest.

Step 5 of 9

Your policy decides

policy.yaml says which severities block the build and which only warn. Exceptions need a reason and can expire.

block_severities: [CRITICAL, HIGH]
warn_severities:  [MEDIUM]
denied_licenses:  [GPL-3.0-only]

Step 6 of 9

One look shows the risk

Each package becomes a tower: taller and redder means riskier. The verdict at the top tells you whether this build would pass.

Step 8 of 9

Every report gets a fingerprint

The result is saved as a CycloneDX report with a SHA-256 hash. Change one byte and the check fails, so nobody can quietly turn a failing scan into a pass.

report.cdx.json

"bomFormat": "CycloneDX",
"depscan:result": "failpass",
"depscan:violations": "3"

SHA-256

report.cdx.json: OKreport.cdx.json: FAILED

Step 9 of 9

It runs on every pull request

Connect the GitHub webhook and each pull request is scanned at its latest commit, with the result posted where reviewers already look.
