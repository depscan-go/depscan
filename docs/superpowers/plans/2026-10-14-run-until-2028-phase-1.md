# Run until 2028, phase 1: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Keep depscan's Azure and GitHub setup running until the end of 2028 without anyone having to remember anything. That means fixing the budget, giving the app headroom, and locking the URL. It also means turning every expiry date into a GitHub reminder, keeping the scheduled workflows alive, and noticing outages and overspending. Finally, the whole team gets access, and a drill proves that a full rebuild works.

**Architecture:** Terraform changes live in `infra/terraform/`, and Sayan applies them. GitHub Actions workflows report everything as GitHub issues, because Azure's notification emails don't arrive on this subscription. The issue logic lives in two small scripts in `.github/scripts/`, so it can be tested locally. One runbook, `infra/RUNBOOK.md`, covers incidents, secret rotation and rebuilds.

**Tech Stack:** Terraform (azurerm `~> 5.8`), GitHub Actions (`actions/checkout@v7`, `azure/login@v3`), bash, `jq`, `yq` (preinstalled on GitHub's Ubuntu runners), and the `az` and `gh` CLIs.

**Spec:** `docs/superpowers/specs/2026-10-12-run-until-2028-design.md`

## Global Constraints

- Every command runs from the repo root. Terraform runs as `terraform -chdir=infra/terraform ...`.
- There is one Azure for Students subscription. Its ID lives only in the gitignored `infra/terraform/terraform.tfvars`. The billing currency is **INR**.
- The Container Apps environment runs in **Express** mode: no Key Vault references, no Container Apps Jobs, public images only, and deploys go by digest.
- Allowed regions: `malaysiawest`, `eastasia`, `koreacentral`, `uaenorth` and `indiasouthcentral` (which has no Container Apps).
- The repo is public. Secrets, email addresses, Azure subscription and tenant IDs, and teammates' IDs never go in it. They belong in `terraform.tfvars` or Key Vault.
- Notifications are GitHub issues that @mention `sayanx64`. Azure alert emails don't arrive on this subscription.
- Uptime checks run at most every 2 hours, to stay inside Azure's free allowance.
- Only Sayan runs `terraform apply`: never Claude, a teammate or CI. Claude writes the Terraform and predicts each plan, and teammates get no access to Terraform's state.
- Commits are authored by Sayan Pal only, with no co-author or "Generated with" lines, and their messages are short.
- PR bodies are 2–4 casual lowercase sentences in Sayan's style, with no headings or tables.
- Merge with `gh api -X PUT repos/depscan-go/depscan/pulls/<n>/merge -f merge_method=merge` once `test`, `lint` and `docker` are green. (`gh pr edit` is broken on this repo.)
- Workflows that log into Azure only work on `main` (a schedule, or a dispatch with `--ref main`). The OIDC trust only accepts `repo:depscan-go@336174858/depscan@1404590227:ref:refs/heads/main`.
- Every workflow change must pass `docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest -no-color <file>`.

## Review Focus

1. **A cold start looks like an outage.** The app scales to zero, so most uptime checks wake it up. Expected: the few seconds it takes to start never open an issue. Pinned in Task 8, step 7.

- [ ] **Step 3: Write the reminder script**

Create `.github/scripts/remind.sh`, then `chmod +x .github/scripts/remind.sh`:

```bash
#!/usr/bin/env bash
# remind.sh EXPIRY_FILE SOON_DAYS
# Opens one GitHub issue for each item in EXPIRY_FILE that's due within SOON_DAYS, or overdue.
# Issues are matched by title, so running it every week doesn't open duplicates.
# Needs GITHUB_REPOSITORY and GH_TOKEN. YQ overrides the yq command; DRY_RUN=1 only prints.
set -euo pipefail
file=$1
soon=$2
today=$(date -u +%F)
read -ra yq <<<"${YQ:-yq}"
open_titles=$(gh api "repos/$GITHUB_REPOSITORY/issues?state=open&per_page=100" \
  --jq '.[] | select(.pull_request == null) | .title')

"${yq[@]}" -o=json '.items' <"$file" | jq -c '.[]' | while read -r item; do
  what=$(jq -r .what <<<"$item")
  due=$(jq -r .due <<<"$item")
  action=$(jq -r .action <<<"$item")
  owner=$(jq -r .owner <<<"$item")
  days=$((($(date -u -d "$due" +%s) - $(date -u -d "$today" +%s)) / 86400))
  if [ "$days" -gt "$soon" ]; then
    echo "later: $what ($due, in $days days)"
    continue
  fi
  title="Reminder: $what ($due)"
  if grep -qxF "$title" <<<"$open_titles"; then
    echo "already open: $title"
    continue
  fi
  if [ "$days" -lt 0 ]; then when="$((-days)) days overdue"; else when="in $days days"; fi
  if [ "${DRY_RUN:-}" = 1 ]; then
    echo "would open: $title, $when"
    continue
  fi
  body=$(printf '@%s %s is due **%s** (%s).\n\nWhat to do: %s\n\nOpened by the Upkeep workflow from `infra/expiry.yaml`. When it is done, move the date in that file and close this issue.' \
    "$owner" "$what" "$due" "$when" "$action")
  gh api "repos/$GITHUB_REPOSITORY/issues" -f title="$title" -f body="$body" --jq '"opened: \(.html_url)"' </dev/null
done
```

- [ ] **Step 5: Write the workflow**

Create `.github/workflows/upkeep.yaml`:

```yaml
name: Upkeep

# Weekly housekeeping: a reminder issue for everything in infra/expiry.yaml that's 30 days
# away or less, and re-enabling the scheduled workflows so GitHub doesn't pause them.
on:
  schedule:
    - cron: "0 3 * * 1" # Mondays, 08:30 in India
  workflow_dispatch:
    inputs:
      soon_days:
        description: "Remind about items due within this many days"
        default: "30"

permissions:
  contents: read
  issues: write # reminder issues
  actions: write # re-enable scheduled workflows

concurrency:
  group: upkeep
  cancel-in-progress: false

jobs:
  upkeep:
    runs-on: ubuntu-latest
    env:
      GH_TOKEN: ${{ github.token }}
    steps:
      - uses: actions/checkout@v7

      - name: Reminders
        env:
          SOON_DAYS: ${{ inputs.soon_days }}
        run: .github/scripts/remind.sh infra/expiry.yaml "${SOON_DAYS:-30}"

      # GitHub pauses scheduled workflows in public repos after 60 days without activity.
      # This runs even when a step above failed: if it stops, every scheduled check stops with it.
      - name: Keep scheduled workflows enabled
        if: ${{ !cancelled() }}
        run: |
          for wf in nightly.yaml watchdog.yaml upkeep.yaml; do
            gh api -X PUT "repos/$GITHUB_REPOSITORY/actions/workflows/$wf/enable"
            echo "enabled $wf"
          done
```

GitHub doesn't document what resets the 60-day timer. Re-enabling through the API is what the widely used keepalive-workflow action does by default, so it's the best evidence we have. It can only be proven by a 60-day quiet stretch. Merged PRs (including Dependabot's, from Task 7) are commits, and those reset the timer anyway.

- [ ] **Step 2: Write the script**

```bash
#!/usr/bin/env bash
# spend.sh LIMIT
# Opens a GitHub issue when Azure's spend for the month so far is over LIMIT, in the billing
# currency (INR here). If the cost API fails, so does this script; that never counts as zero.
# Needs an Azure login (az), GITHUB_REPOSITORY and GH_TOKEN. NOTIFY defaults to sayanx64.
set -euo pipefail
limit=$1
# az rest fills in {subscriptionId} from the current login.
out=$(az rest -m post \
  -u "/subscriptions/{subscriptionId}/providers/Microsoft.CostManagement/query?api-version=2023-03-01" \
  --body '{"type":"ActualCost","timeframe":"MonthToDate","dataset":{"granularity":"None","aggregation":{"totalCost":{"name":"Cost","function":"Sum"}}}}' \
  -o json)
# No rows means nothing has been billed yet this month.
cost=$(jq -r '(.properties.rows[0][0] // 0) * 100 | round / 100' <<<"$out")
currency=$(jq -r '.properties.rows[0][1] // "INR"' <<<"$out")
echo "Azure spend this month: $cost $currency (limit $limit)"
if ! awk -v c="$cost" -v l="$limit" 'BEGIN { exit !(c > l) }'; then
  exit 0
fi
title="Azure spending is high ($(date -u +%Y-%m))"
open_titles=$(gh api "repos/$GITHUB_REPOSITORY/issues?state=open&per_page=100" --jq '.[].title')
if grep -qxF "$title" <<<"$open_titles"; then
  echo "already open: $title"
  exit 0
fi
body=$(printf '@%s Azure has spent **%s %s** this month, over the %s limit.\n\nSee "Azure spending is high" in `infra/RUNBOOK.md`.' \
  "${NOTIFY:-sayanx64}" "$cost" "$currency" "$limit")
gh api "repos/$GITHUB_REPOSITORY/issues" -f title="$title" -f body="$body" --jq '"opened: \(.html_url)"'
```

              gh api -X PATCH "repos/$GITHUB_REPOSITORY/issues/$issue" -f state=closed --jq .state

              gh api "repos/$GITHUB_REPOSITORY/issues" -f title="$TITLE" -f body="$body" --jq .html_url

Use this for a new subscription. It takes about an hour.

1. Log in: `az login`, then `az account set -s <subscription id>`.
2. Register the resource providers: `for ns in Microsoft.App Microsoft.OperationalInsights Microsoft.KeyVault Microsoft.ManagedIdentity Microsoft.Storage Microsoft.Consumption Microsoft.CostManagement; do az provider register -n $ns --wait; done`
3. Make the state storage, and turn on its backups:
   ```bash
   az group create -n rg-depscan-tfstate -l malaysiawest -o none
   SA=depscantf$RANDOM
   az storage account create -g rg-depscan-tfstate -n $SA -l malaysiawest --sku Standard_LRS --min-tls-version TLS1_2 --allow-blob-public-access false -o none
   az storage container create --account-name $SA -n tfstate --auth-mode key -o none
   az storage account blob-service-properties update -g rg-depscan-tfstate --account-name $SA --enable-versioning true --enable-delete-retention true --delete-retention-days 14 --enable-container-delete-retention true --container-delete-retention-days 14 -o none
   echo $SA
   ```
   Then write `backend.hcl` from `backend.hcl.example` with that storage account's name.
4. Write `terraform.tfvars` from `terraform.tfvars.example`. Set `budget_start` to the 1st of the current month, because Azure only accepts a new budget that starts this month or later.
5. Key Vault secrets have to exist before a full plan, but Terraform creates the vault. So build without them first:
   ```bash
   terraform init -backend-config=backend.hcl
   terraform plan -out tfplan -var wire_database_url=false -var enable_webhooks=false -var enable_anchoring=false
   terraform apply tfplan
   ```
6. Store the four secrets in the new vault (see "Rotating a secret"; `terraform output key_vault_name` gives the vault's name). If `az` says Forbidden, wait a few minutes: your role on the new vault takes a while to apply.
7. Run `terraform plan -out tfplan` and `terraform apply tfplan` again, without the `-var` flags. Expect `0 to add, 1 to change`: the app gets its secrets.
8. In GitHub (repo Settings → Secrets and variables → Actions → Variables), set `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID` from `terraform output github_oidc_variables`.
9. The URL has changed, so follow "The URL changed".
10. Run CD once (Actions → CD → Run workflow) to deploy the current image by digest.

## Yearly drill

Once a year, rebuild a full copy next to the real one to prove this runbook still works. The copy uses the prefix `depscandr` and the region `eastasia`. It keeps its state in the same storage under its own key, and gets throwaway secrets. Never point GitHub or a webhook at it. The drill covers steps 5–7 of "Rebuild from scratch" plus the live tests, and takes about an hour.

1. Copy the Terraform outside the repo, so the real folder and state are never touched. From the repo root:
   ```bash
   REPO=$PWD
   DRILL=$(mktemp -d)/terraform
   cp -r infra/terraform "$DRILL" && rm -rf "$DRILL/.terraform" "$DRILL"/*tfplan*
   cd "$DRILL"
   terraform init -backend-config=backend.hcl -backend-config=key=depscan-drill.tfstate
   VARS=(-var prefix=depscandr -var location=eastasia -var 'team_object_ids=[]' -var "budget_start=$(date -u +%Y-%m-01T00:00:00Z)")
   date -u +%H:%M   # start time
   ```
2. Build it without secrets:
   ```bash
   terraform plan -out tfplan "${VARS[@]}" -var wire_database_url=false -var enable_webhooks=false -var enable_anchoring=false
   ```
   The plan must only add resources: `0 to change, 0 to destroy`. Anything else means it's pointing at the real state, so stop. Also check that nothing in it names the real setup: `terraform show -no-color tfplan | grep -cE 'rg-depscan[/"]|depscan-server|kv-depscan-'` must print `0`. Then run `terraform apply tfplan`.
3. Store throwaway secrets. While the server doesn't read `DATABASE_URL`, a placeholder is fine; once it does, use a Neon branch's URL.
   ```bash
   KV=$(terraform output -raw key_vault_name)
   for s in database-url github-token; do az keyvault secret set --vault-name "$KV" -n "$s" --value drill-placeholder -o none; done
   V=$(openssl rand -hex 32); az keyvault secret set --vault-name "$KV" -n webhook-secret --value "$V" -o none; unset V
   (cd "$REPO" && go run ./cmd/depscan keygen -out "$DRILL/drill-key.json" >/dev/null)
   az keyvault secret set --vault-name "$KV" -n solana-key --file "$DRILL/drill-key.json" -o none && shred -u "$DRILL/drill-key.json"
   ```
   If `az` says Forbidden, wait a few minutes and run the command again.
4. Give the app its secrets: `terraform plan -out tfplan "${VARS[@]}"` should say `0 to add, 1 to change, 0 to destroy`. Then run `terraform apply tfplan`.
5. Run the live tests against it: `cd "$REPO" && DEPSCAN_URL=$(terraform -chdir="$DRILL" output -raw app_url) bash e2e/tests/07-live.sh`. Every check should pass.
6. Tear it down. `prevent_destroy` guards the environment and the app, so remove it, but only in the copy:
   ```bash
   cd "$DRILL"
   sed -i '/prevent_destroy = true/d' main.tf
   terraform plan -destroy -out tfplan "${VARS[@]}"
   terraform apply tfplan
   az group exists -n rg-depscandr   # false
   cd "$REPO" && rm -rf "$(dirname "$DRILL")"
   date -u +%H:%M   # end time
   ```
   Never run the `sed` line in `infra/terraform`. If destroying `rg-depscandr` fails because it still holds resources, run `az group delete -n rg-depscandr --yes`, then plan and apply the destroy again.
7. Add a row to the drill log below, and fix any step in this runbook that was wrong.
